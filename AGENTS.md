# WebComPy — AI Agent Reference

> **For development workflow** (OpenSpec, PR process, agent delegation): see [CONTRIBUTING.md](CONTRIBUTING.md).
> This file is the technical reference for AI agents working on the codebase.

## Dual-Environment Architecture (CRITICAL)

This framework operates in two distinct runtime contexts:

- **Browser (PyScript/Emscripten)**: Reactive system, component rendering, DOM manipulation, routing
- **Server (Standard Python)**: CLI tools, dev server (Starlette+uvicorn), static site generator

When modifying code, always consider which context the code runs in.
`platform.system() == "Emscripten"` is used to detect the browser environment.
Code in `webcompy/` (core), `webcompy_server/`, `webcompy_cli/`, and `webcompy_testing/` is context-sensitive.

## Project Structure

- `packages/webcompy/` — Core/browser package (`webcompy` import name)
  - `components/` — Component system (base classes, decorators, generators)
  - `elements/` — Virtual DOM / HTML element system
  - `signal/` — Reactive state management (Reactive, Computed, ReactiveList, ReactiveDict)
  - `template/` — HTML template engine (`render_template`, `{{ }}` interpolation, void/boolean attrs, reactive attributes via `Computed`)
  - `router/` — Client-side routing (history/hash modes)
  - `app/` — Core application class (`WebComPyApp`, `AppConfig`, `RenderContext` ABC)
  - `di/` — Dependency injection system (provide/inject, DIScope, InjectKey)
  - `ajax/` — HTTP client (browser fetch)
  - `aio/` — Async utilities (AsyncResult, AsyncWrapper)
  - `ui/` — Theme system, code blocks, UI components
  - `ports/_browser/` — Browser port implementations
  - `ports/` — Port ABCs and DI keys
- `packages/webcompy-server/` — Server-side package (`webcompy_server` import name)
  - `_html.py` — HTML generation
  - `_context.py` — `ServerRenderContext(RenderContext)`
  - `ports/` — Server port implementations (ServerDOMPort, etc.)
- `packages/webcompy-cli/` — CLI tools (`webcompy_cli` import name)
  - Dev server, SSG, project scaffolding, wheel builder, lockfile management
- `packages/webcompy-testing/` — Testing utilities (`webcompy_testing` import name)
  - TestRenderer, fake ports, ASGI test client, scope helpers
- `docs_app/` — Documentation site application
- `docs/` — Generated static site (gitignored, generated by CI)

## Commands Reference

### Build & Run

```bash
uv sync                                    # Install dependencies
uv sync --all-groups                       # Install all deps (incl. matplotlib/numpy)
uv run python -m webcompy start --dev      # Dev server (default port: 8080)
uv run python -m webcompy generate         # Static site generation
uv run python -m webcompy init             # Project scaffolding
uv build                                   # Build package
```

### Lint, Type Check & Test

```bash
uv run ruff check .                        # Lint
uv run ruff format .                       # Format
uv run ruff format --check .               # Format check
uv run pyright                             # Type check
uv run python -m pytest tests/ --tb=short  # Unit tests only (E2E tests live in e2e/, see below)
uv run python -m pytest tests/ --tb=short --cov=webcompy --cov-report=term-missing  # With coverage
scripts/run-e2e-tests.sh                   # All E2E tests (core + docs, prod + static)
scripts/run-e2e-tests.sh <group-name>      # Single E2E group (e.g., components, docs-home)
scripts/run-e2e-tests.sh --file <path> --serving-mode=static|prod  # Single file via canonical path (e.g., --file e2e/core/test_overlay.py)
scripts/run-e2e-tests.sh --parallel        # All groups in parallel (bounded to half CPUs, safe to always enable)
scripts/run-browser-tests.sh               # Browser unit tier inside a real PyScript runtime
scripts/run-browser-tests.sh --probes      # Environment probe battery only (hard gate)
scripts/run-browser-tests.sh --dual        # + CPython-vs-PyScript dual-run sweep (informational)
scripts/run-browser-version-sweep.sh <ver> # Probe sweep at pinned vs candidate PyScript version
```

### Inspect CLI

Browser-based inspection for debugging and verification. Requires Playwright.

```bash
uv run python -m webcompy inspect serve --config docs_app.webcompy_config --port 0   # Start server
uv run python -m webcompy inspect stop <port>                                          # Stop server
uv run python -m webcompy inspect screenshot <url> [--full-page] [--selector sel]     # Screenshot
uv run python -m webcompy inspect console <url> [--level error]                        # Console logs
uv run python -m webcompy inspect query <url> "h1" [--property text]                   # DOM query
uv run python -m webcompy inspect click <url> "#btn" [--wait-for .result]               # Click
uv run python -m webcompy inspect navigate <url> "/path" [--wait-for "#page"]           # Navigate
uv run python -m webcompy inspect verify <url> --expect "h1=Title"                      # Assertions
```

## CI Pipeline

| Check | Description |
|---|---|
| OpenSpec validation | Validates spec schemas and change artifacts |
| OpenSpec check | Detects completed-but-unarchived changes; validates naming conventions |
| Lint | `ruff check` + `ruff format --check` + browser import-invariant checker |
| TypeCheck | `pyright` |
| Generate | `webcompy generate` on docs_app |
| Test | `pytest` with coverage |
| Browser Tests | `scripts/run-browser-tests.sh`: tests/browser/** inside a real PyScript runtime (allowed to fail initially) |
| E2E | Playwright-based E2E tests (matrix per group/mode) |
| AI Review | `webcompy-reviewer` agent does spec-driven diff review |

On OpenSpec-only PRs (changes under `openspec/` only), code checks (lint through E2E)
are skipped — only OpenSpec validation and AI review run.

## Code Conventions

- Python 3.12+ (aligned with latest PyScript/Pyodide runtime)
- Package management with `uv` — use `uv add <package>` to add dependencies, `uv lock` to update lockfile
- Type annotations throughout (package includes `py.typed` marker and `.pyi` stubs)
- Docstrings are required on all public interfaces under `packages/*/src` (re-exported names and their public members, plus the important-internal allowlist; module summary, Google-style function Args/Returns and class Args/Attributes, re-exported constants via PEP 224 attribute docstrings). New or modified public interfaces in `packages/*/src` MUST carry docstrings; `tests/`, `e2e/`, `docs_app/` are out of scope. No OpenSpec artifact references (spec/change names, `openspec/` paths, task numbers) in docstrings or comments — external standards (RFC, PEP, CommonMark) remain allowed. When modifying any public interface under `packages/*/src`, update its docstring in the same change to keep implementation and documentation in sync.
- No comments in code unless explicitly requested — docstrings are not comments
- Component classes use decorators: `@component_template`, `@on_before_rendering`
- Reactive state primitives are specified in `openspec/specs/reactive/spec.md` and `openspec/specs/composables/spec.md`. New transfer-capable state SHOULD be created via `use_state` / `use_reactive_list` / `use_reactive_dict` composables inside component setup so the SSR transfer path works.

### Naming Conventions

- Public Python functions and variables use `snake_case`.
- Classes and exceptions use `PascalCase`.
- Module-private names use a leading underscore (`_private_name`).
- Constants use `UPPER_CASE`.
- WebComPy composables follow the `use_verb` / `use_noun` pattern in `snake_case` (e.g., `use_state`, `use_router`, `use_async`, `use_async_result`).
- DOM and browser API wrappers may use `camelCase` **only** when intentionally mirroring a standard web API name (e.g., `setAttribute`, `appendChild`, `addEventListener`). Public APIs that are not direct web-standard wrappers must use `snake_case`.

## App Instance API

- `WebComPyApp` is the central application object:
  - `app.run(selector="#webcompy-app")` — Browser entry point (raises if not in Emscripten)
  - `app.di_scope` — DI scope context manager for server-side rendering
- Server entry points use `create_asgi_app(app, server_config=None)` and `run_server(app=None)` from `webcompy_cli`
- SSG uses `generate_static_site(app=None, generate_config=None)` from `webcompy_cli`
- Configuration: `AppConfig` (base_url, dependencies, assets, app_package)
- `app.__component__` is deprecated — use forwarded properties: `app.routes`, `app.router_mode`, `app.set_path()`, `app.head`, `app.style`, `app.scripts`, `app.set_title()`, etc.
- Per-app state: Each `WebComPyApp` owns its own `ComponentStore` and `_defer_*` rendering state
- DI scope is managed via `app.di_scope` context manager — no global `_root_di_scope`

- Do NOT edit files in `docs/` — they are generated output (gitignored, generated by `webcompy generate`)
- The `.pyi` stub file at `webcompy/ports/_browser/_raw.pyi` provides type hints for browser APIs
- `webcompy-cli/src/webcompy_cli/template_data/` contains the project template for `webcompy init`
- Skills live under `.agents/skills/<name>/SKILL.md` as the single source of truth (discovered natively by OpenCode, Antigravity, Codex CLI, Cursor, and Gemini CLI, and symlinked into `.claude/skills/` for Claude Code). Slash commands (`/opsx-*`) live under `.agents/commands/` and are symlinked into `.opencode/commands/` and `.claude/commands/`. Thin permission-sandboxed agent envelopes (`webcompy-reviewer`, `webcompy-inspector`) live under `.opencode/agents/` (OpenCode and CI) and `.claude/agents/` (Claude Code).

## Specifications & Invariants

`openspec/specs/` is the authoritative specification for all framework behavior. Before modifying or reviewing code:

1. Always start with `openspec/specs/overview/spec.md` and `openspec/specs/architecture/spec.md`.
2. Consult [openspec/SPEC_INDEX.md](openspec/SPEC_INDEX.md) for the complete **Framework Invariants**, **File → Spec Mapping**, and **Current Specs** index, and read every owning `openspec/specs/<name>/spec.md` for the files you touch.

## Git Conventions

### Branch Names

```
<type>/<description>   # kebab-case, e.g., feat/add-di-system
```

Types: `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `style`, `perf`.

### Commit Messages

```
<type>: <description>

Co-Authored-By: <harness-name> <noreply@...>
```

Include a `Co-Authored-By:` trailer for AI-assisted commits using the coding harness or tool's standard trailer (e.g., `opencode <noreply@opencode.ai>`, `Claude <noreply@anthropic.com>`, `Antigravity <noreply@google.com>`). Omit the trailer on human-only commits.

### PR Body

When creating a PR, the body MUST follow the template in `.github/PULL_REQUEST_TEMPLATE.md`. Read the template before writing the PR body and fill ALL sections.

### Change Conventions (OpenSpec)

- Change names use `<type>-<short-description>` (hyphen separator, e.g., `feat-list-reconciliation`)
- Proposals MUST include "Known Issues Addressed" (if applicable) and "Non-goals" sections
- Tasks MUST be broken into chunks of max 2 hours

## Agents, Skills, and Slash Commands

Reusable domain knowledge lives in `.agents/skills/` as the single source of truth (symlinked into `.claude/skills/` for Claude Code). All Agent Skills-compatible harnesses auto-load a skill when its `description` matches the task:

| Task | Skill |
|---|---|
| Reactive / browser runtime changes | `webcompy-browser-development` |
| CLI or server changes | `webcompy-server-development` |
| UI component development | `webcompy-component-development` |
| docs_app changes | `webcompy-docs-development` |
| Local CI checks | `webcompy-local-ci` |
| Code review | `webcompy-review` |
| Browser inspection | `webcompy-inspect` |

- **Slash commands**: `/opsx-*` commands live in `.agents/commands/` and are symlinked into `.opencode/commands/` (OpenCode) and `.claude/commands/` (Claude Code). In Antigravity and Claude Code, every skill in `.agents/skills/` is also directly invocable as `/<skill-name>` (e.g., `/openspec-propose`, `/openspec-apply-change`, `/webcompy-review`, `/webcompy-local-ci`).
- **Sandboxed agents**: Two thin envelopes (`webcompy-reviewer`, `webcompy-inspector`) restrict tool permissions and load their companion skill (`webcompy-review`, `webcompy-inspect`). Definitions live in `.opencode/agents/` (used by OpenCode and the GitHub Actions CI review job) and `.claude/agents/` (used by Claude Code). In Antigravity, invoke skills directly or delegate to built-in subagents with the corresponding skill. Prefer invoking a skill directly unless an agent's permission sandbox or subagent context isolation is needed.

## Review Knowledge Maintenance

`openspec/specs/` is the single source of truth for requirements and API naming. Universal docs (`AGENTS.md`, `CONTRIBUTING.*`, `openspec/SPEC_INDEX.md`, `.agents/skills/*/SKILL.md`) SHALL reference specs, not transcribe them. When specs are added, modified, or removed, update:

1. The **File → Spec Mapping** table in `openspec/SPEC_INDEX.md`
2. The **Framework Invariants** list in `openspec/SPEC_INDEX.md` and the **Critical Framework Invariants** section in `.agents/skills/webcompy-review/SKILL.md` (headings + spec references)
3. The **Current Specs** list in `openspec/SPEC_INDEX.md`
4. Any referencing doc whose spec reference now dangles or whose transcribed content is stale
5. Run `python3 scripts/check-doc-spec-refs.py` and confirm it passes (validates spec refs, retired API names, `AGENTS.md` <= 24,000 bytes, and SSOT symlink parity)

When a public API is renamed, add the retired name to the blocklist in `scripts/check-doc-spec-refs.py` so docs referencing it fail validation.

## Language Rules

- All documents (proposals, designs, specs, tasks, PR descriptions, PR titles,
  PR review comments, code comments) MUST be written in English.
- Communication with the user MUST use the language the user prefers. This
  applies to chat output, not to the deliverables above. AI agents that draft
  PR bodies or code comments MUST produce English output regardless of the
  chat language.
